# @zotlit/db

Zotero database layer — Drizzle schema, typed queries, and domain helpers for reading `zotero.sqlite`. App-agnostic: consumers create a client and call the exports; opening the data directory and watching for changes lives elsewhere.

## Commands

Use the root commands for tests and repository-wide lint (root AGENTS.md → Commands). Package-specific tools:

- `pnpm --filter @zotlit/db db:pull` — drizzle-kit pull.

## Clients

Every query, reader and context takes a `ZoteroDatabase` (`src/client/database.ts`, exported from `@zotlit/db`): the Drizzle SQLite database in the synchronous result mode over the Zotero relations. It names no driver, so the engine runs on any synchronous SQLite driver. An adapter makes the client: `@zotlit/db/client/node` over `node:sqlite`, which only a desktop host and Node tests import, and `@zotlit/db/client/wasm` (`src/client/wasm.ts`), which opens a file of a loaded `@zotlit/drizzle-sqlite-wasm` module with the Zotero relations and runs in the Worker zone. `src/client/wasm.test.ts` imports the scenario database into it and compares the readers' results with the Node client's; `vitest.config.ts` resolves sqlite-wasm to its browser build, as the driver package does. A new adapter runs `describeDriverConformance` from `@zotlit/db-testing/conformance` in its test, as `src/desktop/node-client.test.ts` does. The Node client reads each integer of a query with a mapper as a `bigint`, so an integer `sql` field takes a number mapper (`.mapWith(Number)`, or `epochMilliseconds` from `src/item-query/scan-page.ts`), and `src/desktop/number-fields.test.ts` fails on a field without one. The adapter is in `src/desktop/node-client.ts`, because it needs Node; the lint rules of the package allow Node modules only in `src/desktop/`; the `./path` export (`src/lib/zt-path.ts`) joins and normalises paths in pure code with `/` separators.

## Item fields

Field naming follows type-specific names — `BookSectionFields.bookTitle`, not `publicationTitle`. Use `FIELD_ALIASES` from `@zotlit/zotero-types` for type-specific → base-field resolution.

`item.baseFields` carries the same values under their canonical base-field names, resolved against the connected database's own mapping rows so custom item types and custom fields resolve too, and `item.venue` derives the **Venue** from it. `src/queries/_base-fields.ts` owns that mapping for every query that needs it. See [ADR 0026](../../docs/adr/0026-venue-resolves-the-container-role-before-the-publisher-role.md).

`fieldsCombined.custom` drives categorization: `0` = built-in (typed property under `item.fields`), `1` = user-defined or newer (entry in `item.customFields`). See `src/queries/items.ts`.

## Date and language parsing

`item.date` and `item.language` are raw strings — the query layer does not parse them. Consumers call `parseItemDate` / `parseItemLanguage` at the use site; language lookup is caller-provided via `createLanguageLookup()`.

## Template data (`zt` variables)

Read `src/lib/context/note-context.ts` for the public seam and `src/lib/context/` for the assembly pipeline.

### Generated contract artifacts

The `zt` types plus their doc comments are the single source of truth for the template contract. `scripts/generate-contract.ts` extracts them into a contract IR and emits one JSON Schema per data root, both committed under `src/contract/generated/`. `src/contract/roots.ts` holds the Template-slot → root registry the emitter and the Template Workbench CLI share.

- Regenerate with `pnpm --filter @zotlit/db generate:contract` after any contract type or doc-comment change; `pnpm verify`, the gate of `pnpm land`, fails on a stale artifact.
- The extractor parses with ts-morph's vendored frozen TypeScript 6, not the repo's TypeScript 7. See [ADR 0015](../../docs/adr/0015-template-contract-artifacts-generate-from-ts-types.md).
- Three doc tags on a contract member carry emitter data: `@ztFilter <name>` names the Liquid filter of a helper member, `@ztInert` (empty tag) marks a helper the resolver can leave inert, and `@example` holds exactly one fenced code block. Any other content in any tag fails the extractor.

### Template data helpers

`@zotlit/db/template-data` (`src/template-data/`) holds what every host reads Template data through: accessor paths (`formatAccessorPath`), the mark of an inert helper (`markInertPlaceholder`), and `serializeTemplateData`, the JSON-safe contract form the contract IR describes.

## Item Query readers

`src/item-query/` holds every SQL statement of Item Query, behind the `@zotlit/db/item-query` export. It is the only entry that loads `effect`; keep `effect` imports inside it. Define each statement with `defineStatement` in `src/item-query/database.ts` and name its reader: it is the one place where a driver call becomes an Effect, a thrown value becomes `ItemQueryDatabaseError`, and `ItemQueryStatementObserver` (a reference with a no-op default) gets the reader, the parameters, and the rows of each statement. Test readers on the scenario database (`@zotlit/db-testing/scenario`, opened with `connectClient` from `src/desktop/node-client.ts`); `seedBulkLibrary` adds a Library of any size for a test that needs several pages.

Candidate readers select IDs from one Target Library with the caller’s `limit`. `src/item-query/candidate-set.ts` owns Item leaves, `attachments.ts` and `annotations.ts` own element leaves, `relation-candidates.ts` maps elements to parents, and `parent-candidates.ts` bounds Parent Record reads to matching parents and their children. An Item seek leaf uses one statement; a `text-sweep` leaf uses `readTextSweepWindow`, one statement per 2,000 Item IDs on the `itemData` primary key, then the value and Library, with `+fieldID`. The root Item candidate pass reads `readMaxItemID` once for a plan with a sweep and owns its cap, projection, and sparse-Library fallback. Parent Record readers accept seek leaves. An element Tag page uses a bounded index probe and, when full, an ordered page. Parent Record statements have separate reader names. Candidate statements return IDs: the 500-Item limit of one statement applies to the scan page, the universe chunk, and the hydrate chunk; `readUniverseRows` restricts them to the query universe. A Relation List reader (`readItemAttachments`, `readItemAnnotations`, `readAttachmentAnnotations`) reads one keyset page of at most 500 rows after a row of the last page; the Record Loader of `@zotlit/item-query` reads pages until a short one.

A Zotero database has no `sqlite_stat1`, so SQLite starts a join at `items.libraryID = ?` and reads every `items` row of the Library. In a statement that starts at a leaf, an ID list, or an Item ID scan cursor, write the Library term with `unindexed` (`src/item-query/database.ts`), and check the plan with `EXPLAIN QUERY PLAN` on a Stress Build (`pnpm fixture stress --library-items 100000`). Scan pages and universe rows read in ascending Item ID order; scan pages take `afterItemID` (0 for the first page). A scan row holds its timestamps as numbers: a `Temporal` object for each Item of a Library makes long garbage-collection pauses in the Obsidian window.

Resolve the Target Libraries from `readLibraries` (`src/item-query/libraries.ts`). It is the one Library reader: the statement of `getLibraries` (`selectLibraries` in `src/queries/libraries.ts`) through the reader seam, with the one `Library` row shape, so it gives the rows that ZoteroReads and Library Scope get. `getLibraryByGroupID` and the group lookup of the other queries (`groupIDForLibrary`, `resolveGroupID`) use the same statement. The other readers take one Library; a query of several Libraries calls them once for each.

Every table and column a reader statement reads belongs in `ITEM_QUERY_LAYOUT` (`src/layout/index.ts`), or in `OPTIONAL_LAYOUT_COLUMNS` for a column that the reader selects only when the copy has it; add them with each new reader. `defineStatement` runs the layout check before the first statement on each copy, and `src/item-query/layout.test.ts` fails when a statement of a reader module that `src/item-query/index.ts` exports reads outside the manifest.

## Layout of a copy

`src/layout/` is the Layout module. `readDatabaseLayout` reads the columns of each table and view and the `userdata` and `compatibility` stamps of a copy once for each client, logs the stamps, and gives the gaps against the manifest. A reader that selects a column some copies lack asks `layout.has(table, column)`; the stamps are for logging and `getSchemaVersions` only. The core is synchronous and loads no `effect`. `src/item-query/database.ts` runs the same two statements through the reader seam (`readLayout`, `checkLayout`), and `src/item-query/layout.ts` gives `ItemQueryLayoutError` and `checkDatabaseLayout`, the synchronous check that ZoteroReads runs when it validates a client. A copy keeps its first layout for the life of its client: a test that changes the layout of a copy reads it again through a new client.

## Web Library Replica

`src/replica/` (export `@zotlit/db/replica`) builds the Web Library Replica: a database with the Zotero database layout, filled from Zotero Web API records. It is Worker-zone code and writes through the `ZoteroDatabase` it is given, so it runs on any synchronous client. `createReplica` writes the tables and indexes of `layout.generated.ts`, the `version` rows, the vocabulary of `@zotlit/zotero-types/vocabulary` and the identity rows; `applyRecords` stores and removes the collections and items of one library by key inside the caller's transaction and reports each object it defers or skips.

- The replica connection runs with foreign keys off, as sqlite-wasm opens it; `applyRecords` throws on a connection with `pragma foreign_keys` on. The writer deletes every child row and unused value, creator and tag itself and never relies on `ON DELETE CASCADE`; `src/replica/integrity.test.ts` runs `pragma foreign_key_check` after re-apply, replacement and deletion on both clients.
- `layout.generated.ts` copies the DDL of the tables the readers use from the pristine Zotero database (`packages/scripts/lib/fixture/pristine-zotero.sqlite.gz`). The table list is in `scripts/generate-replica-layout.ts`; a table a new reader reads goes there. Regenerate with `pnpm --filter @zotlit/db generate:replica-layout`; `src/replica/create.test.ts` fails when the module differs from the pristine database.
- The mapping follows the Zotero client at commit 213b0d7d7 (AGPL-3.0): the field, creator, tag, note, attachment and annotation rules of `Zotero.Item.prototype.fromJSON` and the item save, and `_updateGlobalSchema` for the vocabulary IDs. Change a rule together with its source there.
- A stored value equals the value that the desktop client stores after its own sync of the same record. `@zotlit/zotero-compat` computes the values that the client derives from a field: the field text, the single-line field value, the ISBN, the multipart date, the note text, wrapper and title, the access date and the item dates, the creator, tag and collection names, the annotation values and colour, the attachment path and read time. Its guide maps each function to its client source and Zotero tests, and holds the one table of the known differences from the client; change those rules there.
  - A date field follows `Zotero.ItemFields.isDate` (`xpcom/data/itemFields.js:190`): a field with metadata in the vendored schema has the type of its own metadata; a field without metadata has the type of the base field that it maps to. `dateFieldsOf` of `@zotlit/zotero-types` applies this rule to make `ZOTERO_VOCABULARY.dateFields`. It reads the month names, day suffixes and day order of the client locale that `applyRecords` and `applyStagedPasses` get as `locale`, a Zotero language name such as `fr-FR`; `strToMultipart` of `@zotlit/zotero-compat` resolves it, and `en-US` is the one default, in that package. The stored date of an item does not change with the locale: a new locale reaches the stored dates only through a full rebuild of the replica.
  - An access date that `accessDateToSql` leaves out is logged and not stored. An item date that `isoToSql` does not read gets the time of the apply.
  - The time of the apply is the `now` of `applyRecords` and `applyStagedPasses` (the sync engine gives its own); without it, `applyRecords` reads the present time once. It fills, as UTC SQL time to the second (the form of SQLite's `CURRENT_TIMESTAMP`), the item dates that `isoToSql` does not read, `collections.clientDateModified`, and `dateDeleted` of `deletedItems` and `deletedCollections`: these are all the columns of the replica layout with a `CURRENT_TIMESTAMP` default. Two applies of the same records with the same `now` give equal rows.
  - A group attachment gets `itemAttachments.lastRead` from the personal library's synced setting `lastRead_g<groupID>_<key>` when the setting changes after the attachment is stored, as the client's `attachmentReadObserver` does; the item record keeps it.
- The replica is deliberately more tolerant than the client's strict sync (`fromJSON(..., { strict: true })`): where the client's save throws and the object waits in its sync queue, the replica stores what a reader can use and logs or reports the rest, and skips an item of an unknown item type, annotation type or link mode as a `ReplicaProblem`. `src/replica/apply.test.ts` states each case.
- The sync of `@zotlit/web-library` stages its downloads in `replicaSync*` tables of the same file (`src/replica/sync-tables.ts`), which no reader reads and the layout check does not name. `src/replica/sync-store.ts` writes them, and `applyStagedSteps` moves the finished passes into the Zotero tables in bounded steps inside a transaction that the caller holds. Keep these rules there:
  - The first apply records the language it parses dates in (`replicaSyncMeta('zoteroLocale')`), and a later apply in another language fails, unless the staging replaces the whole replica (`replacesLocale`, a rebuild).
  - A library that the key no longer reads is staged as `remove`; the apply removes a group's rows and clears the personal library, which keeps its `libraries` row at version 0.
  - Each pass records the key's note permission and whether it is a rebuild, and the apply commits the permission with the library version. A download reuses a staged pass only when both equal the present sync's, and sets each complete pass back to downloading, so the apply takes only the passes that the present sync completed (`reconcileStagedLibraries`).
  - The apply of a rebuild pass first clears the committed objects of its library and then applies the staged pass, so it writes what a fresh build of the same staged state writes (local IDs included); an incremental pass keeps the last good row of an object it skips or defers.
  - The read times of group attachments come from the personal library's `lastRead_g` settings, which the apply keeps in `replicaSyncReadTimes` and writes to every group attachment at the end of each apply, so an attachment that arrives after its setting gets its read time.
  - `ensureSyncTables` adds the columns and the read-time table that a replica file made before them lacks.
  - Each library result says whether readers can see its change (`changed`).
  - An object that `applyRecords` defers stays staged for the next pass of its library; a skipped one waits for a newer vocabulary.
  - The staging keeps its rules at each step, rollback and stop: `stagingViolations` of `@zotlit/db/replica/staging-invariants` (`src/replica/__fixtures__/staging-invariants.ts`) names each rule, `src/replica/staging-invariants.test.ts` holds each one, and the suites of `@zotlit/web-library` and `@zotlit/zotero-reads` run it after each step.
- `src/replica/parity.test.ts` holds the readers equal on the scenario database and on a replica built from its Web API records (`@zotlit/db-testing/web-api`). `@zotlit/db/replica/parity-pair` gives the pair to the parity tests of Item Query and item lookup; it names each change it makes to the scenario database and each column parity leaves out (`PARITY_LEAVES_OUT`). Each entry of that list is in one of two states: the reader layout lacks it, and for a column `parity.test.ts` writes another value into the replica and holds every reader result unchanged. Local numeric IDs differ between any two Zotero databases; the parity tests compare by key.
