# @zotlit/zotero-reads

ZoteroReads: the asynchronous RPC between a ZotLit plugin's renderer and the Web Worker that owns the Zotero database ([ADR 0068](../../docs/adr/0068-the-zotero-database-runs-in-a-web-worker-behind-zoteroreads.md)). The ZotLit host composes it; the standalone ZotLit Reader does not run it. Glossary: `apps/obsidian/GLOSSARY.md`.

## Layers

Each layer is one folder of `src/` and one runtime zone ([ADR 0117](../../docs/adr/0117-runtime-zones-are-checked-by-the-module-graph.md)): `contract/` and `worker/` are the Worker zone, `client/` the Obsidian zone (`zotlit.layers` in `package.json`), and `desktop/` the desktop zone. A new file goes in the folder of the runtime that loads it. A layer imports the layers below it: contract ← worker, contract ← client, and all three ← desktop. The runtime check (`pnpm run lint:runtime-zones`) holds the zones, and `oxlint.config.ts` keeps `contract/` and `client/` from importing `worker/`. Lint refuses Node built-in imports and the Node globals outside `desktop/`.

- `contract/` — the `ZoteroReads` RpcGroup (`rpc.ts`), its schemas and codecs, and the value types both sides share: Library Scope, the Query Job codec, the citation lookup answer, the `Changes` feed, the Item Snapshot (`snapshot/`). Worker zone: it loads in a Web Worker on each host.
- `worker/` — the handlers that answer the RPCs from a `ZoteroDatabase` (`handlers.ts`), the readers they use, the `Connection` they borrow (`connection.ts`), the in-process adapter, the Item Snapshot export (`snapshot/`, which takes its revision hash from the host), and `serveZoteroReads` (`serve.ts`) for a host's Worker entry. The worker modules are in the Worker zone, with no DOM, host module or Node: the host passes in its database opener, file system, Chinese Segmenter read, Item Query adapter (`QueryJobRunner`) and Item Snapshot revision hash.
- `client/` — the renderer side: the `ZoteroReads` service (`service.ts`), the Worker client (`worker-host.ts`), leases, events and view atoms. It loads on Obsidian Mobile, with no Node or Electron.
- `desktop/` — the desktop host's database source: Read Mode, clones of `zotero.sqlite`, fingerprints, file watches and the refresh lane (`source.ts`, `read-source.ts`), the `node:sqlite` handle (`node-client.ts`) and Replica Driver (`replica-driver-node.ts`), the sha256 revision hash of the Item Snapshot (`snapshot-revision.ts`), and the sweeps of read clones (`reap-temps.ts`). Only a desktop host imports it.
- `__fixtures__/` — test support for this package and its consumers: `in-process.ts` (in-process clients, openers), `reads.ts` (the service over a test transport), `citation-lookup.ts` (lookup answers), `reads-seed.ts` (the seed of the handler suites), `web-api.ts` (a seed served by the fake Zotero Web API, and the Web API source on the wasm memory driver), `web-api-reads.ts` (the service over the Web API source), `replica-store-suite.ts` (the Replica Store suite of each driver adapter), `replica-counts.ts` (count guards), `replica-apply-worker.ts` (a Worker stopped mid-apply), `worker-channel.ts` (Worker roots over a channel).

A host writes its Worker entry with `serveZoteroReads`, giving its `Connection` layer, Item Snapshot revision hash and platform. The desktop plugin's entry is `apps/obsidian/src/services/zotero-reads/worker.ts`; the app's Vite config bundles it as the embedded Worker.

The online library has two Worker roots over `serveWebApiReads` (`worker/serve-web-api.ts`) and the `ZoteroReadsWeb` RpcGroup (`contract/web-worker-rpc.ts`): desktop's `serveZoteroReadsReplica` (`desktop/serve-replica.ts`), a branch of the desktop Worker, and the web root `serveZoteroReadsWeb` (`worker/serve-web.ts`, entry `src/worker/zotero-reads-web-root.ts` of `@zotlit/obsidian`), whose wasm engine comes from the Resource Pack. Plugin and Workers are one build, so their protocol has no version.

The Query Job and its answer belong to the host's Item Query adapter. The contract carries them through `ItemQueryTypes` (`contract/item-query.ts`), which the host fills by declaration merging.

## The Web API source

`worker/web-api-source.ts` (`layerWebApiSource`) is the `Connection` over the Web Library Replica and the `WebLibrarySync` service behind the settings page ([ADR 0120](../../docs/adr/0120-the-web-library-replica-runs-on-one-connection-with-a-driver-for-each-platform.md)). It keeps the plan, the consent, the state machine, the Backoff pauses and the download of `@zotlit/web-library`. The Replica Store (`worker/replica-store.ts`) keeps the storage rules on one connection from a Replica Driver (`worker/replica-driver.ts`; adapters `worker/replica-driver-wasm.ts`, `desktop/replica-driver-node.ts`), which sets the pragmas of its platform. The renderer (`LibrarySource` of `@zotlit/plugin-services`) drives the refreshes and the account consent; the Worker has no timer.

- **State.** The availability is one state machine, `worker/web-api-machine.ts`: `transition` is the only code that changes it, and `SyncStatus`, the read state and the change events are its projections. After a change to its events, regenerate `worker/web-api-machine.table.md` with `pnpm exec turbo run @zotlit/zotero-reads#generate:machine-table`.
- **Plan.** Each sync checks the key first and lets `plan` (`worker/replica-plan.ts`) choose a first build, an incremental sync, a rebuild, a wait for consent or a refusal.
- **Invariants.** A change here keeps each of these; the named suite holds it.
  - A failed sync keeps the last good replica readable and names the problem only in `SyncStatus` (`web-api-source.test.ts`, "keeps reads ready on the last good replica").
  - A rebuild for a new Zotero language downloads the whole account into the staging while readers read the old replica, and replaces it in one apply only when every library downloaded (`web-api-source.test.ts`, "while a language rebuild downloads"). A rebuild for another account empties the replica first, so that account's data is never readable while the new one downloads.
  - An apply is one transaction in slices on the one connection. It begins only when no borrow is held, after the hold-back of the read gate; borrows wait from `begin` to `commit`, and `empty` and `remove` wait the same way (`replica-store.test.ts`; `worker/read-gate.test.ts`). The store also holds a borrow while the replica loads or recovers and fails it while the source is degraded.
  - The download writes the staging through `stage`, one transaction for each write. Status and `SourceIdentity` answer from the last commit, read at the open and at each commit (`replica-store.test.ts`, "answers the libraries", "lists only the libraries").
  - The store has one state (`report()`). A failed rollback reopens the file once no borrow is held; if that fails, the store is unavailable and the source degrades (`replica-store.test.ts`, "opens the file again", "tells the source").
  - The commit, a renewed client (or a reopened file) and the `changed` event are one uninterruptible step that never rolls back the commit. A sync with no reader-visible change keeps the client and sends no event (`web-api-source.test.ts`, "keeps the client object and emits no change"); a failed checkpoint is a status problem only.
  - A `Backoff` or `Retry-After` deadline holds for every later request to the same Zotero address, also in the next sync (`web-api-source.test.ts`, "keeps the Backoff deadline").
  - The API key appears in no log, error, event or status (`web-api-source.test.ts`, "prints no API key").
  - A stop at any point leaves a replica that converges on the next start, with no account's data deleted and no other account downloaded without consent (`worker/web-api-crash.test.ts`). The memory storage in Node cannot leave a journal behind, so a stopped Worker's journal is proven only on real OPFS in a host.
- A borrow during the first build waits with no time limit; while the replica loads or applies, `pendingIdentity` answers `SourceIdentity` without a borrow.
- The Citation Lookup build and the item index (`layerUnpinnedConnectionItemSource`) borrow once for each window or page, and start again on a new client (`worker/background-borrows.test.ts`).

## Tests

From this package directory, `pnpm exec vitest run src/<layer>/<file>.test.ts` runs one file. The suites run in Node over `node:sqlite`, and the handler suite of `worker/zotero-reads.test.ts` runs a second time over the Web API source, with an expectation for each source where a result differs; the client suites read the Obsidian kit through the Obsidian mock of `@zotlit/obsidian-kit/vitest`. The End-to-end Run proves the real Worker transport.
