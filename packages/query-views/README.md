# Item Query adapter

The adapter is in this package's `src/worker/item-query/` and `src/desktop/item-query/`. The Worker part runs in the ZoteroReads Worker, under each source: the Query Job (`job.ts`), its answer (`answer.ts`), the encoder of the answer document (`encode.ts`), the Worker protocol (`worker-protocol.ts`), the Query View request (`query-view.ts`), the CLI Datasets (`datasets.ts`), the attachment file probe (`attachment-files.ts`), the trace (`trace.ts`) and the part of the CLI contract that the answer writes (`contract.ts`: command names, `DEFAULT_CLI_LIMIT`, the diagnostics and the envelope). The host-free part holds the file port of an export (`src/core/item-query/export-files.ts`). The desktop part holds the flags and the rejection diagnostics of the CLI (`contract.ts`), the decode, the guide, `QueryService`, the decoder of the answer stream (`read-answer.ts`), the delivery module (`delivery.ts`) and the Node adapter of the file port (`export-files-node.ts`). The paths below name files in `src/worker/item-query/` unless stated otherwise. `QueryService` is its only Promise edge: it runs each Query Job as a fiber and maps Obsidian's `AbortSignal` to fiber interruption there.

- Command names and `DEFAULT_CLI_LIMIT`: `contract.ts`; the flags: `src/desktop/item-query/contract.ts`. The CLI Datasets (`datasets.ts`) and the guide (`guide.ts`) read them there; the guide also prints `defaultFields` and `defaultSort` of the `ITEMS` descriptor of `@zotlit/item-query`.
- The Target Libraries and the query run in one Effect (`encodeCommand` in `answer.ts`) inside the ZoteroReads connection scope. The Query Job (`job.ts`) provides the borrowed client as `ItemQueryDatabase` and gives the captured envelope identity to the answer. Every choice of Libraries is a `LibraryScope`: the one in force (`scope` of `AnswerJob`, a value of the `QueryJob`), All Libraries for `library=all`, or Selected Libraries for the selectors in `library`. `encodeCommand` resolves it with `resolveLibraryScope` on the rows of `readLibraries`, read on the borrowed client of the query. It is the one Library reader: `LibraryScopeService` gets the same rows through `getLibraries`. A named scope needs each of its Libraries (`requireEach`). A run without its Target Libraries fails with `TargetLibrariesUnavailable`; `failureDiagnostic` in `answer.ts` maps its `reason` to `library-not-found`, `source-unavailable`, or `no-library-available`.
- CLI argument decoding: `decodeQuery` in `src/desktop/item-query/decode.ts`. `QueryService` decodes once in the renderer, claims the query id from the decoded value, and sends the `DecodedQuery` in the `QueryJob`; the worker handlers take the `DecodedQuery`. Keep `DecodedQuery` plain JSON, with an omitted argument as an absent key: the RPC accepts only JSON values.
- A diagnostic code of the adapter and its recovery text: `DIAGNOSTIC_HINTS` in `contract.ts`; the guide prints that list.
- The production CLI query and schema run through `QueryService` and the ZoteroReads RPC handler. The worker holds one connection borrow through execution and delivery; Query Rows and Temporal values stay inside the worker. `consumeQuery` delivers projection chunks sequentially to `createDocument` in `answer.ts`, which gives them to the encoder, `encodeAnswer` in `encode.ts`; each write finishes before the next projection chunk is read. The engine's `collectQuery` collects the same chunks into the complete result, for callers outside the adapter. The encoder receives only a function that takes each text piece of the document.
- Three tasks, three owners ([ADR 0121](../../docs/adr/0121-the-window-delivers-a-zotlit-query-answer.md)): the query engine runs the query, the Worker encodes the answer document (`encodeCommand` in `answer.ts`, `encodeAnswer` in `encode.ts`), and the window delivers it (`deliver` in `delivery.ts`). The Query Job holds no limit, no file and no flag of its root.
- The answer stream: `zotlit:query` (inline and export), `zotlit:query-values` and `zotlit:query-schema` cross to the window through the stream request `QueryAnswer` of ZoteroReads. Its order is one `Head` with the summary of the answer (the envelope with no rows and no values), then the `Chunk` parts with the UTF-8 bytes of the document, then a `Trace` with the Worker measurement of a measured run, which `answerStream` finishes after the reader takes the last chunk. A failure of the command is the error of the stream, `QueryFailed` with the diagnostic of the answer and the Worker measurement of a measured run. `encodeCommand` in `answer.ts` runs the command and gives its summary and its text pieces to a sink, in the format of the export (`json`, `csv`, `tsv`) or as the JSON envelope; `answerParts` and `answerStream` in `job.ts` turn them into parts of about 256 KiB, each a new buffer, through a queue with no buffer, so the Worker waits for the reader of each part. The client call reads with a stream buffer of 0 (`bindReads` in `@zotlit/zotero-reads/client/service.ts`), so the Worker is at most one chunk ahead of the window. The handler takes a query slot and then the borrow in the scope of the stream, so a queued job holds no borrow, and the borrow lasts until the stream ends. The delivery module decodes this order in one place: it gives the summary, the document as a stream of chunks, and the trace; a stream that breaks the order is a defect there.
- Delivery: `deliverAnswer` in `src/desktop/item-query/delivery.ts` takes the command, a target (inline, or a file path with its format), the answer stream, the file port of the host and the observer of a measured run, and has no Node import. It reads the answer stream, gives the Worker measurement to the observer, and owns the cancel rule of an export (below) and the inline limit, `INLINE_MAX_BYTES` (1 MiB of UTF-8): it reads one chunk at a time and stops the document at the first chunk above the limit, so the stream closes and the Query Job and its borrow end early. A measured run (`zotlit:query-measure`) above the limit reads the rest of the document and drops it, so the measure command gets the Worker measurement. A file target goes to the file port; with no port it answers `export-unavailable` before it starts the answer stream, so no job goes to the Worker. It answers the delivered text or the receipt envelope (`fileReceipt` in `contract.ts`: the summary of the `Head` and the delivered file, with its path, byte count and format). `QueryService` chooses the target and maps a failure to its envelope: `source-unavailable` for a borrow that fails, the diagnostic of `QueryFailed`, `result-too-large` (with the recovery action of the command, from `deliveryDiagnostic` and `RESULT_TOO_LARGE_HINTS` in `contract.ts`), `output-error` with the message of the system, or `export-unavailable`. The Worker holds no inline limit and no file. A Query View and the custom-field read keep the unary `ItemQuery` request.
- The file port: `ExportFiles` in `src/core/item-query/export-files.ts`, one operation `write(path, document)` that resolves with the bytes of the new file. Each adapter keeps one contract, which `src/__fixtures__/item-query/export-files-suite.ts` tests: the file appears complete or not at all, an existing file stays, a failed or interrupted document leaves no file, and a document that fails before its first chunk fails with its own error. The host composition gives the adapter: the desktop feature (`src/desktop/feature.ts`) passes `nodeExportFiles` to `layerQueryService`. The Node adapter writes `<output>.<pid>-<uuid>.zotlit-partial` beside the output, commits with a hard link in one uninterruptible step, and removes the staging file in each outcome; before it opens one, it sweeps the folder of the output and removes each staging file whose process is not live and that is older than 1 hour.
- A Worker root gives the job runner its `QueryJobRoot` (`makeQueryJobRunner` in `job.ts`): a `QueryMeter`, the async context and the heap reading of its runtime. The three Worker roots compose the runner in the same way, so the library source has no effect on what a command can do. The desktop Worker root passes `nodeQueryMeter` (`src/desktop/item-query/node-meter.ts`: `node:async_hooks` and `process.memoryUsage()`) through `queryJobRunner` (`src/desktop/item-query/job.ts`). The Web Worker root (`apps/obsidian/src/worker/zotero-reads-web-root.ts`) passes an empty meter: a slice there holds the job's Effect evaluation in one turn of the Item Query scheduler, work in host callbacks outside Effect is not counted, and the measurement has no heap figures. Each meter keeps its own count of running jobs and its own host callback state. The Worker file system serves only the attachment file probe: under the Web API source the Worker has none, and each probe gives `exists: false`.
- The envelope names the source of the borrowed client: the ZoteroReads handler passes `Connection.identity(client)` to the runner, and the job stamps it into the CLI envelopes only (a view or custom-field job does not read it). A failed read of the identity answers `database-error`. The job holds no rule about sources; the `SourceIdentity` type and its rules belong to `@zotlit/zotero-reads`.
- Byte counts: a file receipt counts the bytes that the adapter writes (`ExportFiles.write` gives them), which equal the size of the file. The inline limit counts the UTF-8 bytes of the chunks that delivery reads.
- A CLI Query Job is one fiber in the window, and its exit is the outcome: answered, cancelled or failed. `QueryService` forks it uninterruptible and claims its id. `deliverAnswer` reads the answer stream of an inline job in an interruptible region. For an export job it makes only the wait for the `Head` and each read of a chunk interruptible: a cancel by id, an unload or an interrupted call interrupts the read, closes the stream and sends the interrupt to the Worker, which ends the job and its borrow; the adapter then removes its staging file. The commit, the trace and the receipt run in one protected region, so the commit wins a late cancel. The window settles when it has sent the interrupt. The interrupt of the answer stream is the one cancel of a CLI job: the Worker keeps no registry of CLI jobs, and the window sends no `CancelItemQuery` for them. Gate G3 of ADR 0121 measured the cancel of a running export at 50,000 Items: in two runs, each timer and `zotlit:query-cancel` case of the query measure settled within 12 ms of its request, against a limit of 50 ms.

  | Phase                                 | A cancel in this phase                     |
  | ------------------------------------- | ------------------------------------------ |
  | The id is claimed                     | cancelled                                  |
  | Waiting for a slot and for the borrow | cancelled; no borrow starts                |
  | Running and delivering                | cancelled; no file; the borrow ends        |
  | Commit of the export file             | the commit wins; the answer is the receipt |
  | Answered                              | no effect                                  |

- A unary Query Job (a Query View, the custom-field read) is one fiber in the worker, and the job type of `ItemQuery` holds only these typed jobs: `runQueryJob` in `job.ts` runs it on `ItemQueryScheduler` with the database of the job. The ZoteroReads handler keeps the fiber in a `FiberMap` by job id, from the wait for a slot to the answer; `CancelItemQuery` and an interrupted request both interrupt it.
- Keep a JSON file byte-identical to `JSON.stringify(envelope, null, 2)`, the inline answer. A `format=csv` or `format=tsv` file holds one line for each row in its place: `delimitedRows` in `encode.ts` writes it through `@zotlit/shared/delimited`, with each value as `valueText` gives it.
- Responsiveness measurement checks renderer timer gaps across execution, the transfer of the chunks, and the file write and publication in the window. Execution slices and encoding steps retain the spec's limits in the worker. Bulk values cross to the renderer only as byte chunks of about 256 KiB: both a large result graph and a large transferred string can block the renderer through allocation and garbage collection.
