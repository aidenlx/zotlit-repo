# Item Query adapter

The adapter is in this package's `src/worker/item-query/` and `src/desktop/item-query/`. The Worker part runs in the ZoteroReads Worker, under each source: the Query Job (`job.ts`), its answer (`answer.ts`), the Worker protocol (`worker-protocol.ts`), the Query View request (`query-view.ts`), the CLI Datasets (`datasets.ts`), the attachment file probe (`attachment-files.ts`), the trace (`trace.ts`) and the part of the CLI contract that the answer writes (`contract.ts`: command names, `DEFAULT_CLI_LIMIT`, the diagnostics and the envelope). The desktop part holds the flags and the rejection diagnostics of the CLI (`contract.ts`), the decode, the guide and `QueryService`. The paths below name files in `src/worker/item-query/` unless stated otherwise. `QueryService` is its only Promise edge: it runs each Query Job as a fiber and maps Obsidian's `AbortSignal` to fiber interruption there.

- Command names and `DEFAULT_CLI_LIMIT`: `contract.ts`; the flags: `src/desktop/item-query/contract.ts`. The CLI Datasets (`datasets.ts`) and the guide (`guide.ts`) read them there; the guide also prints `defaultFields` and `defaultSort` of the `ITEMS` descriptor of `@zotlit/item-query`.
- The Target Libraries and the query run in one Effect (`answer` in `answer.ts`) inside the ZoteroReads connection scope. The Query Job (`job.ts`) provides the borrowed client as `ItemQueryDatabase` and gives the captured envelope identity to the answer. Every choice of Libraries is a `LibraryScope`: the one in force (`scope` of `AnswerJob`, a value of the `QueryJob`), All Libraries for `library=all`, or Selected Libraries for the selectors in `library`. `answer` resolves it with `resolveLibraryScope` on the rows of `readLibraries`, read on the borrowed client of the query. It is the one Library reader: `LibraryScopeService` gets the same rows through `getLibraries`. A named scope needs each of its Libraries (`requireEach`). A run without its Target Libraries fails with `TargetLibrariesUnavailable`; `answerFailure` in `answer.ts` maps its `reason` to `library-not-found`, `source-unavailable`, or `no-library-available`.
- CLI argument decoding: `decodeQuery` in `src/desktop/item-query/decode.ts`. `QueryService` decodes once in the renderer, claims the query id from the decoded value, and sends the `DecodedQuery` in the `QueryJob`; the worker handlers take the `DecodedQuery`. Keep `DecodedQuery` plain JSON, with an omitted argument as an absent key: the RPC accepts only JSON values.
- A diagnostic code of the adapter and its recovery text: `DIAGNOSTIC_HINTS` in `contract.ts`; the guide prints that list.
- The production CLI query and schema run through `QueryService` and the ZoteroReads RPC handler. The worker holds one connection borrow through execution and file closure; Query Rows and Temporal values stay inside the worker. `consumeQuery` delivers projection chunks sequentially to the encoder, `createAnswer` in `answer.ts`; each write finishes before the next projection chunk is read. The engine's `collectQuery` collects the same chunks into the complete result, for callers outside the adapter. Small responses return inline, bounded by `INLINE_MAX_BYTES`. The encoder receives only a writer.
- A Worker root gives the job runner its `QueryJobRoot` (`makeQueryJobRunner` in `job.ts`): a `QueryMeter`, the async context and the heap reading of its runtime, and `writesFiles`, whether it can write an export file. The desktop Worker root passes `nodeQueryMeter` (`src/desktop/item-query/node-meter.ts`: `node:async_hooks` and `process.memoryUsage()`) and a file writer through `queryJobRunner` (`src/desktop/item-query/job.ts`). The Web Worker root (`apps/obsidian/src/worker/zotero-reads-web-root.ts`) passes an empty meter and no file writer: a slice there holds the job's Effect evaluation in one turn of the Item Query scheduler, work in host callbacks outside Effect is not counted, and the measurement has no heap figures. Each meter keeps its own count of running jobs and its own host callback state. Without a file writer, a query with `output` answers `export-unavailable` before the borrow, and `result-too-large` gives a hint that does not name `output`. Under the Web API source the Worker has no file system: each attachment file probe gives `exists: false`.
- The envelope names the source of the borrowed client: the ZoteroReads handler passes `Connection.identity(client)` to the runner, and the job stamps it into the CLI envelopes only (a view or custom-field job does not read it). A failed read of the identity answers `database-error`. The job holds no rule about sources; the `SourceIdentity` type and its rules belong to `@zotlit/zotero-reads`.
- A runner can refuse a job before the borrow (`QueryJobRunner.refused`): on a root that writes no file, a query with `output` answers `export-unavailable` without waiting for the database.
- Byte counts: a file receipt counts the bytes that the writer encodes and writes (`QueryWriter.write` gives them). The inline limit refuses as soon as the characters pass `INLINE_MAX_BYTES` and checks the UTF-8 length of the complete text once at the end (`exceedsInlineLimit`).
- One Query Job is one fiber in the worker: `runQueryJob` in `job.ts` runs it on `ItemQueryScheduler` with the database of the job. The ZoteroReads handler keeps the fiber in a `FiberMap` by job id, from the wait for a slot to the answer; `CancelItemQuery` and an interrupted request both interrupt it. The staging writer is an `acquireRelease` in the scope of the job, so it closes before the borrow ends; an interrupt lands between two chunks, and the open, each write, and the close of the file run to their end. The answer carries a `QueryReceipt`: `QueryService` publishes a `file` receipt and removes the staging file when the job ends. Its job fiber is uninterruptible outside the wait for startup and the wait for the worker, so publication wins a late cancel. An interrupt in the wait for the worker sends `CancelItemQuery` and waits for the answer, so the request settles after the worker closes its writer and ends its borrow. Keep a JSON file byte-identical to `JSON.stringify(envelope, null, 2)`. A `format=csv` or `format=tsv` file holds one line for each row in its place: `delimitedRows` in `answer.ts` writes it through `@zotlit/shared/delimited`, with each value as `valueText` gives it.
- Responsiveness measurement checks renderer timer gaps across execution, response transfer, and file publication. Execution slices and encoding steps retain the spec's limits in the worker. Keep bulk values in the worker: both a large result graph and a large transferred string can block the renderer through allocation and garbage collection.
