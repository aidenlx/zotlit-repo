# Item Query shares execution between collection and incremental delivery

> Amended 2026-10-10 by ADR 0071: the operations take one of three Query Datasets, `ITEMS`, `ATTACHMENTS`, and `ANNOTATIONS`, and Relation Lists are hydrated only when a request names them.

> Amended 2026-10-10: the operations take a Query Dataset. `@zotlit/item-query` exposes `collectQuery(dataset, request)`, `consumeQuery(dataset, request, begin)`, and `describeQueryCustomFields(dataset)`, with the descriptor values `ITEMS` and `ANNOTATIONS`; `queryItems`, `consumeQueryItems`, and `describeItemQueryCustomFields` are their Item forms under the old names. The descriptor carries every fact that differs between the two datasets (names, defaults, Sortable Fields, filter registry, hydration), so the request planner, the diagnoser, the schema description, and the Obsidian adapter branch on no dataset flag. The Attachment-file resolver of an Annotation Query arrives as an Effect reference, on the pattern of the tuning service. The shared execution path, the database and clock services, and the cancellation and delivery rules below are unchanged.

`@zotlit/item-query` exposes `queryItems`, `consumeQueryItems`, and `describeItemQueryCustomFields`, each returning an Effect (Effect v4). The query operations share one execution path that hides parsing, validation, planning, candidate narrowing, hydration, evaluation, sorting, projection, cancellation, and truncation behind one interface. The build-only `@zotlit/item-query/schema` entry generates the static Item Query Schema from the same registries that execution uses; `describeItemQueryCustomFields` reads the active source's custom-field capabilities. Compilation stages, evaluator values, planner tuning, and relation loading remain implementation details.

The database arrives as a service from `@zotlit/db`, which owns every SQL statement as Effect-native readers over the borrowed `NodeDatabaseClient`; `@zotlit/item-query` contains no SQL. Zotero SQLite is a local-substitutable dependency, so tests cross the same readers on a Zotero-made database. The Query Clock also arrives as services: the Effect `Clock` and an Item Query time-zone reference. The Obsidian adapter is the only Promise edge: `ItemQueryService` runs each Query Job as a fiber and maps Obsidian's `AbortSignal` to fiber interruption at that one `runPromise`; the worker runs the job on the time-budget scheduler as a fiber in the ZoteroReads handler, and `CancelItemQuery` interrupts that fiber. ZoteroReads owns the connection scope and supplies the borrowed client and captured identity directly. The Obsidian adapter owns the resolution of the Target Libraries, CLI decoding, its 100-row default, Temporal wire serialization, and the versioned envelope, and it runs each operation on the time-budget scheduler that the package exports.

A successful Query Result includes the normalized Item Query, Query Rows, `returnedCount`, and `truncated`. Projection values use one recursive `ProjectionValue` type. An invalid request fails with one typed `ItemQueryError` carrying a stable code, location, message, and recovery hint. An unsupported database layout and a database failure are separate typed failures, cancellation is fiber interruption, and an implementation failure is a defect. Every sort runs in memory, so the public sort contract does not depend on SQL ordering.

The Obsidian query adapter runs queries, schema reads, projection, and JSON encoding in the ZoteroReads Web Worker of ADR 0068. The worker borrows its current connection for each query and releases it after execution and file closure. Two query slots bound retained query memory while other ZoteroReads operations keep serving. Query Rows and Temporal values remain in the worker; only bounded JSON answers and export receipts reach the renderer.

Each request has an internal job id. `CancelItemQuery` interrupts that job, including a query waiting for a slot. The original request settles after the writer closes and the connection borrow ends. The renderer then removes the staged file and releases the caller's id. The Query Job of the worker closes the staging writer in its scope before RPC settles; `ItemQueryService` publishes and removes the staging file. The encoder only writes chunks. A successful export closes its staged file before the renderer publishes it without replacing an existing destination. Cancellation before publication removes the staged file; successful publication wins a concurrent cancel. Plugin disposal cancels and drains query jobs before ZoteroReads disposal. Worker failure and recovery follow ZoteroReads.

Cooperative scheduling alone cannot bound renderer garbage-collection pauses, and transferring a complete large JSON string back into the renderer can itself block the interface. Worker isolation and bounded replies address both causes. Responsiveness measurement checks renderer timer gaps throughout the worker call, including result transfer and file publication. Execution slices and encoding steps retain the spec's 16 ms p99 and 32 ms maximum limits in the worker; renderer gaps are an additional check against those limits. Total-time and cancellation budgets still apply.

Cancellation is cooperative at the engine's scheduler yields and file writes. A hung worker follows the shared ZoteroReads heartbeat and recovery path; a query does not terminate the worker used by the other readers. Measurement aggregates statement events and heap samples in the worker before returning compact diagnostics to the renderer.

`consumeQueryItems` starts a consumer after ordering establishes the normalized request, count, and truncation. It hydrates and projects one chunk, awaits the consumer write, and then proceeds. A successful end returns the consumer's value; consumer failure or interruption stops further reads. `queryItems` collects these same chunks into the complete Query Result. The CLI encodes them directly into bounded inline text or an unpublished file, so an export retains one projected chunk rather than every projected value. Unlimited ordering still retains the compact matches and sort keys.

## SQLite reader bounds and value fidelity

The database package puts its Effect-based SQL readers behind `@zotlit/db/item-query`. Reuse a prepared statement per client. Chunked reads use fixed placeholder slots and bind unused slots to null so the statement shape stays constant. Execute a statement and notify its observer in one synchronous step. A test or measurement can count statements and rows without adding a cancellation point between the read and its report.

Zotero copies lack SQLite planning statistics. On scans, candidate joins, and ID-list reads, keep the Library predicate outside the indexes with unary plus so SQLite starts from the requested IDs, leaf, or scan cursor. Check that a scan does not sort each Item ID page into a temporary B-tree. In exact field candidates, the untyped `itemData.valueID` joins to `+itemDataValues.valueID` so the planner can find a value first and use the `itemData.valueID` index. Apply the field-ID list after the value lookup.

Candidate sets can include Child Records and trashed Items. Restrict them to the Query Dataset's universe and evaluate the full predicate before returning a match. Request one more candidate than the cap to detect an over-budget set. Derive the cap from the count of all rows in the Target Library, including child and trashed rows. Bound Parent Record reads before expansion and report whether matches remain unchecked. Bound each text sweep statement by an Item ID window on the `itemData` primary key. Read the maximum Item ID once to terminate the sweep. The comparison excludes null IDs from a window.

Scan rows carry milliseconds as numbers, with null for a timestamp SQLite cannot parse. Allocate Temporal objects after narrowing to avoid per-Item allocations during a full Library scan. For field values, cast SQLite integers to text inside SQL to preserve all 64 bits. Keep SQLite REAL values in numeric form until the reader converts them to JavaScript strings. A candidate lookup uses numeric bindings only when the input round-trips to the same spelling. Use BigInt for the signed 64-bit integer binding so digits survive the index lookup. Values such as `012` remain text-only.

Read field vocabulary and collection paths once per query for the applicable source or Target Library. Resolve base fields with the database's own type-specific aliases and prefer the type-specific value when both forms are stored. Use the primary creator type of each Item Type to mark creators. Hydrate only the requested values and relations. An absent field has no entry, and an absent relation requested by the caller has an empty list.

## Candidate plans and scan retention

Choose the candidate plan independently for each Target Library. A candidate set must include every record that can match. The evaluator always decides the result. An AND plan can narrow with any complete branch, and can intersect several. An OR plan needs every branch within the cap. Negation does not supply a candidate set. Incomplete reads fall back and their reason distinguishes work-budget exhaustion from a candidate cap. Ask for a look-ahead row to distinguish a complete read at a page boundary from a partial one.

Prefer pure seeks, then mixed branches, then pure sweeps. Skip sweep branches of an AND after a seek supplies a complete set. Use a SQLite LIKE pattern as a superset of both JavaScript string match operations. Replace literal wildcards and case-sensitive ambiguities with wildcards, and skip a pattern with no narrowing content or above SQLite's 50,000 UTF-8-byte limit. Text sweeps run only at the Item Dataset root. Each window is one reader Effect, so the scheduler can yield between statements. Skip sparse Libraries and fall back when the observed or projected match count exceeds the cap.

Load only filter, sort, and group fields in the scan pass. A match retains its scan row, sort keys, and Library index. A bounded result retains at most the limit plus one match per group, in addition to the active page and hydrate chunk. The extra match proves truncation. An unlimited result keeps sorted runs and merges them in steps. Hydrate projection fields only for returned rows. Use the same scan and candidate evaluation and order the combined Libraries together.

Order missing sort values last in both directions. Break final record ties by Indexed Key. A Zotero Key has a fixed length so comparing the bare keys first gives the same order, and matching keys from two Libraries then compare by Indexed Key. When distinct group strings collate equally, compare code units to keep group order independent of read order. Tuning changes the amount of work done per step and the plan chosen while preserving the Query Result.

## Candidate plan verification

Check candidate results against the evaluator, including long membership lists, sparse Libraries, literal wildcards, and Unicode folding. Use expected keys independent of the folding being tested. Use the production scheduler for the 10,000-argument membership test, because a per-operation pause would add many host tasks. The large Parent Record case has a longer timeout to accommodate fixture seeding and reading. Count work at the reader seam so unrelated children and children from other Libraries cannot silently exhaust a selective plan's budget.

## Source reads and record hydration

Give each query one source cache and keep completed reads. Load the field vocabulary only when requested and memoize Collection paths by local Library ID. Candidate lowering reads only the source values already loaded. Collection warnings use the same cache even when no record loader needs the paths. A leave-out request with Formulas checks their custom fields during planning. The fail path can report a missing custom field during request loading.

Resolve a possible dotted custom field against the source before reporting an unknown name. A known dotted field needs bracket access, so the correction covers the complete field name in the original expression. If that name is absent, keep the original property fault when one exists. Check the filter first, then projection paths, grouping, and Formulas.

Build the load requirements once for each pass. Include the dependencies of any Formula the pass reads, and load Query Group data during the scan. Deduplicate Parent Records by source ID within the active chunk. Identity can require a parent even when it needs no additional fields. Reuse Relation List scan rows and hydrated values across nested loads within the root chunk while the loader's needs are fixed. A list may exceed the parent chunk, so use bounded child hydration. Read every Relation List page needed by the evaluator. The candidate work budget does not apply to these lists because they supply the values needed to decide a match.

Read the Query Clock once. Take the instant from Effect's Clock and the time zone from the query reference, which defaults to the host's Temporal time zone. Every calendar-day operation in the query uses that zone. Put each consumer's state in begin, after final ordering, even for an empty result. Deliver one group per chunk, waiting for each write before projecting the next. Call end only after all writes succeed. The typed result includes the number of distinct matches before the limit. The CLI envelope omits it.

## Time-budget scheduling

Give each run its own scheduler because it holds the current slice. Use a 4 ms budget to leave margin for the next synchronous reader under the 16 ms responsiveness target. An operation-count scheduler can let a query block the renderer because a small count can include expensive synchronous reads. Resume in a MessageChannel task to avoid timer clamping and return to the host between slices. Close the channel once no resume waits. An open listener can keep a Node process alive. A test or measurement can observe both sides of each pause with the scheduler's monotonic time. The default observer has no side effects.

## Integration test boundaries

Use `packages/item-query/src/query-items.test.ts` to compare candidate and forced-scan results for large integers and a SQLite REAL whose JavaScript string denotes a different exact integer. Read the bound ID slots when testing hydration. The page cursor is a separate parameter. A projection-only relation loads only returned IDs, and a requested sort field can load before projection. Test a failed reader after a successful layout check so the failure exercises the statement path.

Test the candidate cap against each Library's total rows, including rows that the universe drops. Keep fixture cases whose candidate count fits one Library's cap and exceeds another's to verify independent plan selection. Include a valid candidate set that spans multiple universe and hydration chunks.

Incremental consumption supplies the full match count to the consumer summary. The collected Query Result omits that count. Keep each execution's row state separate, including a repeated execution of the same Effect. Await each write and end the operation on a failed write without starting another projection read.

## Parity and resource tests

Use the statements and pauses from the two observer services to test execution bounds without a wall-clock assertion. Warm the layout check before comparing statement indices on a shared database copy. Count distinct Item IDs for hydration because one row can carry one field value of an Item. Test candidate statements at the cap plus one look-ahead row. The resource fixtures include thousands of Annotations under one parent to distinguish the child page size from the distinct-parent cap. Check that candidate fallback stops the candidate read and that hydration reads every needed child. Compare merge steps by their observed pauses and check the same sorted result for every step size. For cancellation, abort in the statement step or in the host task that ends a pause. The interrupted fiber may take one final pause, and it must start no further statement.

Use the forced Library scan to compare complete wire results and typed failures for each plan and chunk size, including Libraries on opposite sides of their caps. The cases in `packages/item-query/src/scenario-queries.ts` also pin Indexed Keys derived independently from the scenario seed so a regression shared with the scan can fail the suite. Exercise pause methods separately from semantic parity. Run a parity check after dropping the Tag and field-value indexes to show those indexes affect only the plan's cost.

Count retained rows through `WeakRef` in `packages/item-query/src/retention.test.ts`. Keep V8's optimizing compilers off for that file. A pending compilation can temporarily keep a page or chunk alive through its closure. Collect twice at a statement boundary because the first collection can finish marking that started while the previous page was live. Take the projection sample after the scan releases pages and retains matches. Grouped queries retain up to the limit plus one per group. After a run resolves, yield a bounded number of host tasks and collect again to check that the runtime releases the last chunk.

Limit static Query Schema values to the build entry and its description modules. The runtime entry can export schema types. It supplies function definitions to in-process editors, and the generated Query Schema supplies the agent contract. Read custom-field capabilities from the active source. Use the database readers' typed failures on the public query operations.

Use equality or membership in a literal list to lower an Indexed Key selection for one Library. A computed or invalid member leaves selection to the evaluator. Check those paths and shared semantics on both the highest and lowest supported Zotero layouts. Read-only tests can share a scenario copy. A mutating test opens its own. Test suspension across reader boundaries with a deterministic cost per statement. A pause callback can abort while the fiber is still waiting to resume. Observers can omit recorded statements so the test harness releases observed rows. Capability sweeps use the production scheduler because yielding after every operation adds a host task per step. Large relation-budget fixtures have a longer timeout because they seed and read up to 10,000 records.
