# Services

The `zotlit-services` lint rules cover the mechanical part of the service architecture. The reviewer checks the rest:

- **Effect shape.** An Effect service's tag shape is Effect-native: its methods return `Effect`s, each method with arguments through `Effect.fn("<Tag>.<method>")`, or `Effect.fnUntraced` on a per-message or per-item hot path (the Effect runtime section below; `effecttsgo/effect-fn-opportunity` checks it); a member with no arguments is an `Effect` value traced with `Effect.withSpan("<Tag>.<member>")` (`effecttsgo/lazy-effect` reports a zero-argument method), and state others watch is a `changes` Stream. Its layer is a `layer<Name>` export beside the tag (`layerUseLedger`), or a `layer<Name>(deps)` function when it takes plain inputs (`layerLogOutput(plugin)`).
- **Bridge.** Callers outside Effect — the plugin shell and the edge handles — hold the tag's service itself and the plugin runtime's `bridge` (an `EffectBridge`, `@zotlit/plugin-kernel/effect-bridge.ts`). `createShellRuntime` (`packages/plugin-shell/src/obsidian/runtime.ts`) reads shell services once; feature `handles` read their services through the supplied `read` capability; consumers type their deps as a `Pick<Release["Service"], …>` beside a `Pick<EffectBridge, …>`, and run each call through it: `bridge.runSync(…)`, `bridge.runPromise(…)`, `bridge.subscribe(stream, …)`; a module whose Effect body plain code runs receives `{ context, bridge }`, the `Context` of every tag that body `yield*`s, with plain values such as the `App` beside them (`PandocExportDeps`), and a `*Deps` bag of services takes this shape when work touches its module; [Unload](unload.md) gives what unload does to each run and how its caller answers. Nothing else calls `runtime.runSync` / `runtime.runPromise`, which fail or rebuild after unload: a callback that needs a service gets it read once at build. Each edge shape has one helper: an Effect calls a legacy Promise port through `portCall` (`packages/obsidian-kit/src/legacy-port.ts`), whose `LegacyPortError` keeps the rejection as its cause, and a modal callback runs on a runner built over the bridge with `Effect.provideContext` (`runBatchWith`, `packages/notes/src/obsidian/batch/batch-run.ts`). The bridge is the migration seam, not the target: a consumer that converts to Effect yields the tag and drops its `bridge` dep, until the bridge is left only where a callback from outside Effect (an Obsidian event, a React handler) enters it.
- **Edge handle.** Views and legacy callers that a later slice converts may hold an edge handle in place of the tag's service and the bridge: one object per tag built by its feature’s `handles` over the bridge (`bindItemLookup`, `packages/plugin-shell/src/obsidian/platform.ts`). Each member runs one call through the bridge and maps its Exit to the caller's answer (`valueOr`); the handle holds no other logic. A member whose call has no released answer runs through `bridge.runPromise`, so the caller gets the value or the failure. A new handle has a test that it resolves with the result and, after unload, settles as the bridge does. A handle may also serve Effect functions over several tags (`bindNoteActions` for the note commands and menu entries) until its callers convert. A handle may serve the Effect functions of one feature (`bindTemplateData` for the Template data reads) until its callers convert.
- **Views.** A view reads Effect services through view atoms in the plugin's view registry (`@zotlit/obsidian-kit/view-atoms.ts`), keeps its own state in a per-leaf model with pure transitions, and runs its gestures on the leaf's view runner ([ADR 0082](../docs/adr/0082-obsidian-views-read-effect-services-through-view-atoms.md)). The view makes the runner in its constructor (`makeViewRunner`, `packages/obsidian-kit/src/view-runner.ts`) and disposes it once when it closes, which interrupts every Effect still running. `run` forks a gesture and answers its Fiber; `provide` hands a host member the view services; `joinOnView` joins a run for a caller outside the view; `inFlightSlot` lets a second press join the run in flight; `latestSlot` lets a newer run interrupt the one before; `answerOf` answers an Obsidian override's Promise. Its pattern catalogue and pitfalls are in the ADR; a view that converts drops its store and its `bridge.subscribe` calls.
- **One contract per service.** Every caller reads the service's tag: Effect code `yield*`s it, and code outside Effect uses the bridge above (`zotlit-services/no-plain-service-adapters`, `packages/config/oxlint-plugin-services.ts`).
- **Engine in a layer.** A state machine with concurrency of its own is Effect code in its layer: the Zotero Local API session (`packages/plugin-services/src/obsidian/zotero-local-api/session.ts`) keeps its state in `Ref`s, shares one request in flight between callers through a slot, as the Capability Probe does, and a caller that joins it retries when it ends interrupt-only, so each caller ends only on its own interrupt; it queues work per key with a `Semaphore`, runs background work on the layer's Scope, a notice or deferred announcement included, as a fiber on the layer's `FiberSet` (`Effect.yieldNow` first when the order matters), with state in `Ref`s rather than in closures that call a runner, bounds a request with `Effect.timeoutOrElse`, reads the `Clock`, and cancels by interruption rather than by `AbortSignal`. A large state machine that coordinates none of that is Effect functions over one state record that its layer builds: the Annotation Repository core (`annotation-repository/core/`) takes the `CoreState` as its first parameter, `yield*`s the services the record holds (`ZoteroLocalApi["Service"]`, `ZoteroReads["Service"]`, `QueryClients["Service"]`), and publishes its events through a callback the layer turns into Streams. The layer's members `yield*` the core functions. Callbacks that a library calls (TanStack Query read and mutation functions) and the `Disposable` that `hold` answers are its edges, and run through `scopedBridge`, the bridge over the layer's own Scope.
- **Effect services only.** Every plugin service is an Effect service: a tag and a layer in a feature's `serviceGroup`, which the plugin shell (`@zotlit/plugin-shell/obsidian/compose.ts`) composes into the plugin's runtime. `zotlit-services/no-legacy-service` rejects a class that extends `Service`.

## Effect runtime

Review Effect code against the docs of the installed `effect` package, the version the code runs: `node_modules/effect/AGENTS.md`, and the topic folders of `node_modules/effect/ai-docs/src/` — `01_effect` (basics, Schema, services, errors, resources, running), `03_stream`, `04_integration/10_managed-runtime.ts`, `08_observability`, `09_testing`. Cite the doc for each finding. A departure from a documented pattern carries a comment that names its reason.

The Effect lint configuration is in `packages/config/oxlint.base.ts` and this app’s `oxlint.config.ts`. Review the lifecycle, failure handling, interruption, and behavioral proof that mechanical rules cannot establish. Fix warnings introduced by the change.

`zotlit-effect-tests/typed-fake` (`packages/config/oxlint-plugin-effect-tests.ts`) reports a test fake behind a cast. Review what it cannot see: a fake carries only the members its test reads, and a fake that several tests share is one double in its service's `__fixtures__.ts` (root `policies/testing-strategy.md` → Service fakes).

`zotlit-effect-style/no-tacit` (`packages/config/oxlint-plugin-effect-style.ts`) reports a function passed by name to an Effect combinator, such as `Effect.map(fn)`, and `flow`: write the lambda `(x) => fn(x)` (Effect v4 code style → Avoid Tacit Usage).

Check in particular:

- **Service methods** return Effects, and callers outside Effect go through the plugin runtime's `bridge` ([Services](#services) → Bridge); a view's plain code goes through its view runner ([Services](#services) → Views). Every service method with arguments is traced `Effect.fn("<Tag>.<method>")` (`01_effect/01_basics/02_effect-fn.ts`, `01_effect/03_services/01_service.ts`), a generator or a body that returns an Effect; `effecttsgo/effect-fn-opportunity` reports a method that is not. A member with no arguments is an `Effect` value, not a method (`readonly refresh: Effect.Effect<…>`), traced with `Effect.withSpan("<Tag>.<member>")`: `Effect.gen(function* () {…}).pipe(Effect.withSpan(…))`, or the Effect itself when it is already lazy (`Effect.sync(…)`, `Ref.get(ref)`). It runs again on each `yield*`, as an `Effect.fn` body does; a body that reads mutable state while it builds the Effect goes in `Effect.suspend`. `effecttsgo/lazy-effect` reports a zero-argument method. A method on a per-frame or per-message hot path (per worker message, per stream chunk, per item in a loop that runs many times) is `Effect.fnUntraced` instead, with a comment that names the path. The rule is off in tests and fixtures (`*.test.*`, `*.bench.ts`, `*.browser-test.ts`, `__fixtures__`): a test double of a method stays a plain function, and a double of a zero-argument member is an Effect value (`Effect.suspend(spy)` when a test counts its runs). `Effect.fn` runs its body when the Effect runs, not when the method is called, so work that must happen at call time stays outside the body.
- **Crossing in** from plain code runs through the plugin's `ManagedRuntime` (`buildRuntime` in `packages/plugin-kernel/src/effect-layer.ts`); a view crosses in through its view runner (`@zotlit/obsidian-kit/view-runner.ts`). An Obsidian event enters a layer from the source's capability tag (`changes`, narrowed with `filterTag` and handled with `forkEach`); a capability tag registers it through `obsidianEventSource`, and an event from a source with no tag yet enters through `obsidianEvents` ([Events](events.md)); any other Obsidian callback registered there runs through a runner made from the layer's own context (`Effect.runSyncWith(yield* Effect.context<never>())`), so it keeps the layer's services and Clock.
- **Failures** are typed in the error channel as `Schema.TaggedError`s and handled where a decision is made, by tag (`catchTag`). A member's failure type is the real failure type of the core it runs, without the failures that `recover` or the core already removes; `orDie` is for a failure that cannot happen, with a comment that says why. A boundary that must not fail catches the whole `Cause` (`catchCause`) and logs it. A boundary that lets interrupts pass and maps other failures to a fallback uses `recover` (`packages/plugin-kernel/src/effect-cause.ts`); a boundary that reports an outcome uses `reportOutcome` (`packages/obsidian-kit/src/notifier.ts`). Unknown persisted data decodes through `Schema` (`decodeUnknownOption` to degrade).
- **Time** and dates: lint holds the date rule (`zotlit-services/temporal-in-effect`, `clock-time`, `dateGlobals` in `packages/config/oxlint.base.ts`). Review what it cannot see: `@zotlit/db` rows keep `Temporal.Instant`, the template contract, and Effect code passes them on as is; an Effect value reaches plain code as `Temporal` through `packages/plugin-kernel/src/worker/effect-clock.ts` (`toInstant` in `packages/template-workbench/src/desktop/view/preview/render.ts`). Plain code that only measures an instant against its own clock reads it by `epochMilliseconds`, which `Temporal.Instant` and `DateTime.Utc` both carry (`CopyInstant` in `packages/annotations/src/obsidian/annotation-repository/capability-copy.ts`), so Effect and plain callers share it without a conversion. A plain file that imports `effect-clock` counts as Effect code.
- **Cancellation**: an API that returns an Effect cancels by interruption and takes no `AbortSignal`. Where a native or Promise API inside it needs a signal, `Effect.tryPromise((signal) => …)` or `Effect.abortSignal` (aborted when its Scope closes) gives it one. A plain caller that holds a signal — a modal's cancel, the plugin's unload, a CLI run — turns it into an interrupt at the edge with `runPromiseExit(effect, { signal })` and rejects with `signal.reason` where the signal ended the run. A test cancels by interrupting the fiber (`Fiber.interrupt`, or `interruptUnsafe` from inside the run) and expects an interrupt exit; a test of a plain API models the signal's holder with a plain helper. A modal that an Effect waits on opens through `awaitModal` (`packages/obsidian-kit/src/effect-modal.ts`) or `awaitConfirm` (`packages/obsidian-kit/src/confirm.ts`), so an interrupt closes it. `effecttsgo/abort-controller-in-effect` reports a controller made inside Effect code.
- **Interruption**: a step that must finish once started — applying a configuration, a write with its own cleanup — is `Effect.uninterruptible`, and its test proves a scope close waits for it.

## Logging

Log through Effect, with the category set by `withLogCategory` from `@zotlit/plugin-kernel/effect-log.ts` (under parent `["zotlit", "obsidian"]`) and fields as annotations. `zotlit-logging/effect-logging-only` enforces it ([Logging](../../../policies/logging.md)):

```ts
Effect.logWarning("Could not read the saved Uses; starting empty").pipe(
  Effect.annotateLogs({ error }),
  withLogCategory("use-ledger"),
);
```

Plain code runs the same record: on its bridge (`bridge.runSync(...)`) when it holds one, otherwise with `Effect.runSyncWith(logServices)(...)` (`logServices` from `@zotlit/plugin-kernel/effect-log.ts`). A file that only logs this way stays plain code for the Effect-code rules.

`layerLogging` in `packages/plugin-services/src/obsidian/log/service.ts` sets the plugin logger's level and sinks (the console and `zotlit.log.jsonl`); the dev-only `enableStartupLogging` is the one other caller. Outside the logging layer's life, error and fatal records go to the console. The ZoteroReads worker logs through Effect and posts each record over a port (`packages/plugin-kernel/src/worker/effect-log-port.ts`); the host re-emits it into the renderer's Effect logger at the plugin's log level. The citation-parse worker has no logger.
